DASHComponent Guide - Executive dashboardExpand guide
What it is

The home screen: the headline results, a summary strip (the ribbon) worked out from the latest run, and the history of every run.

How it is calculated

Touchless rate = payments posted on their own, divided by all payments in the run (hard payments are counted, not hidden). Unapplied cash = the total of leftover amounts across the run's matches. Latency = the average solver time stored on each match.

What it means

If the unapplied-cash figure grows from run to run, money is arriving faster than the agent can explain it. That points to poor remittance data, not a weak solver.

OPERATE — 04 / RECONCILIATION

Run Reconciliation

The engine matches each payment to invoices. Open any match to see the full evidence for that decision.
JD LINKThe role asks for custom algorithms for matching and reconciliation. This page is that engine, running live on the active case.
Step 1 - narrow the list: for each payment, the engine first narrows the unpaid invoices using the evidence it has, in this order: invoice references in the remittance, then the purchase order, then a known payer alias, then that payer's own invoices. The solver never searches the whole ledger. Step 2 - solve: the MILP solver picks the set of invoices whose total, after discounts and any accepted deduction, equals the payment exactly (the cash conservation equation). Among exact sets it prefers older invoices, and it treats any unexplained leftover (residual) as very costly - a penalty of 1,000,000 - so it would rather propose nothing than hide a difference. Open any match to see its invoices and a why-not check for an invoice it did not pick. An invoice used by one payment cannot be used again in the same batch, and sending the same batch twice replays the first result instead of posting twice.

RUNComponent Guide - Batch reconciliationExpand guide
What it is

One full pass of the real engine over a set of payments: narrow the candidates, solve the matches, judge deductions, and raise exceptions for the rest.

How it is calculated

For each payment: the candidate list narrows by reference, then PO, then payer name. The solver then finds the invoice set that equals the payment exactly, preferring older invoices. The confidence rule and the auto-post rule are on the Methodology page, and every match shows its own worked calculation (its derivation).

What it means

AUTO_POSTED rows are finished work. PROPOSED rows are the agent asking a person to approve. Exceptions are the agent refusing to guess - each one says what to do next.

What you can do

Open any match to read its worked calculation and to test why another invoice was not picked. To change behaviour, edit the rules in Policy Studio and run again.

INSIGHT — 07 / EVALUATIONS

Evaluations

Two lenses, both computed live. First, the active case graded against the answer it stated up front. Second, the solver benchmarked against a simple baseline on labelled cases where the correct answer is known.
JD LINKThe role asks for applied data science with results that can be measured. This page measures the solver and the models against answers that were fixed before the run.
Each test case has a correct answer marked by a human: the invoices the payment truly settles. Both solvers get the same shortlist a real payment would get. Accuracy counts how often the solver's choice equals the marked answer; the exact rate counts answers that leave $0.00 unexplained. The greedy baseline is fast and sounds reasonable, but it fails when the right choice depends on age and deductions together - that is why real payments use the MILP solver.

Request path of one payment

Step Stage What happens
1Ingestion + transformCSV or API payload is normalised to the canonical schema: synonym header mapping, source fingerprinting, row quarantine with reasons. Remittance text goes to the parser (Gemini when configured, deterministic otherwise) and every extracted reference is verified against the open ledger.
2Candidate resolutionThe ledger narrows in order: explicit references, purchase order, payer alias, subsidiary. Duplicates are fingerprinted and stopped before matching.
3MILP solver (HiGHS via scipy)Subset selection under the cash conservation equality with the age-weighted, penalty-priced objective from the Methodology page. A Rust subset-sum kernel mirrors the combinatorics and is equivalence-tested against the Python path on 203 shared cases.
4Deduction intelligenceClaims are classified to the ERP reason taxonomy, z-scored against history, and decided by the expected-value dispute rule.
5Posting + exceptionsExact, confident matches auto-post (simulated posting in this build, labelled as such); everything else becomes a proposed match or a tracked exception with counterfactuals. All of it lands in the audit log with the run's policy snapshot.
6Insight layerDelay and validity models (scikit-learn, time-ordered holdout) feed the forecast bands and the collections queue; the copilot answers only from these stored records, with citations.

Design rules that hold the system together

1. AI proposes, math decides. No LLM output can post cash; it can only propose fields that deterministic components verify.
2. Money is integer cents. No floats anywhere near a posting; residuals are exact, never rounding artefacts.
3. Every decision carries its derivation. If a number cannot be recomputed from records the product shows, it is not shown.
4. Exceptions are a workflow, not a failure. The tail is where analysts earn their keep, so it is designed first-class: counterfactuals, recommended actions, audit trail.
5. Policy is configuration. Thresholds that change behaviour live in tenant policy, versioned with each run - never buried in code.

Scaling the solver

Question Answer
Why doesn't the MILP explode?The solver never sees the ledger. Candidate resolution prunes each payment to a payer-scoped shortlist first (references, PO, alias, payer), so the NP-hard core runs on a handful of invoices per payment, not thousands.
Raw vs prunedA 20-invoice pool has 2^20 (about a million) raw subsets; resolution typically prunes to under 10 candidates, and HiGHS branch-and-bound closes the rest. The Rust subset-sum kernel mirrors the same combinatorics for the fast path.
Latency evidenceSolver time is stored on every match; the Dashboard ribbon averages it for the latest run. The live run streams each payment's solve time as it happens.
EquivalenceThe Rust kernel and the Python solver are proven identical on 203 shared cases; neither is trusted on its own say-so.

Product thesis

01/
The problem

Cash application is a conservation problem with an information problem on top: every cent received must land somewhere auditable, but the evidence arrives as messy remittance text, short pays and silent deductions. Incumbent platforms advertise 85 to 99 percent auto-match, yet implementations run for months and the exception tail still eats the analyst day. The tail is the product opportunity.

02/
The design rule

AI proposes, math decides. Probabilistic components (LLM parsing, ML delay and validity models) extract and score; deterministic components (the MILP solver under a cash conservation equation, the policy engine, the expected-value dispute rule) make every posting decision. Anything unreconciled becomes a tracked exception with counterfactuals - never a silent write-off.

03/
The wedge

A pilot called the replay: send us your last 90 days of payments and open invoices as CSV. AutoCash replays them and shows, cent by cent, what would have auto-posted, what would have been disputed, and what your team touched that it should not have had to. Proof before platform.

04/
North-star metric

Touchless cash rate at $0 residual. Supporting: match accuracy on labelled evaluations, residual dollars, exception ageing, dispute recovery value, solver latency.

Roadmap, honestly labelled. Live ERP write-back (SAP, Oracle, NetSuite), bank-file ingestion (BAI2, MT940, lockbox formats), persistent multi-tenant storage, and SOC 2 are the known table-stakes gaps for enterprise sale. This build covers the decision core those integrations feed: matching, deductions, forecast, collections, evaluation and audit.

Honesty labels. All data in this workspace is synthetic and labelled as such. Market figures quoted anywhere in this product are vendor claims used as context, never this product's results. Win probabilities in deduction intelligence are transparent heuristics, and the UI says so where they appear.
